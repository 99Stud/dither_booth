## Update the booth software

The booth runs a [release](/docs/start-here/glossary/#releases). Updating installs the next one next to it, switches, checks that the booth came back, and goes back on its own if it didn't. How: [Updates](/docs/architecture/updates/).

**From admin:** **System → Software → Update to …**. The panel shows each step and how it ended: [Update the software](/docs/maintenance/system/#update-the-software). The booth needs internet, and `sudo booth service` must have run once with a CLI that has `booth update` (`booth doctor` says **Admin can't update or roll back the booth** until then).

**Over SSH**, the same job:

<Steps>

1. **Update:**

   ```bash
   sudo booth update          # the latest release
   sudo booth update 0.8.0    # or a given one, pre-releases included (0.8.0-rc.1)
   ```

   It downloads the release, checks it against its `SHA256SUMS`, unpacks it, backs up the database, then restarts the apps on it: guests can use the booth until that restart. It installs the release's own `booth` CLI first and applies its system setup (`booth service`, `booth network setup`) on its own.

2. **Read how it ended:**

   - **Updated to 0.8.0.** Done.
   - **Nothing changed, the booth still runs …** The update stopped before the switch (no internet, no such release, a broken download, not enough room). Fix the reason given and run it again.
   - **Rolled back to …** The new release didn't come up within 2 minutes, so the booth went back to the one before, database included. The reason is in the message and in `journalctl -u 'ditherbooth-update@*'`.

3. **Check:**

   ```bash
   booth doctor
   ```

   Then a test print from the Darkroom and one full visit.

</Steps>

### The first update of a booth

A booth set up before releases runs a git checkout, built in place: `booth doctor` says **Runs a git checkout, not a release**. Its first `sudo booth update` turns it into a release. The checkout moves to `/opt/dither-booth-releases/legacy-<version>`, kept to roll back to, and its certificates and logs move to `/opt/dither-booth-shared/`. Before that first update, install a CLI that has `booth update`: see [Update the CLI](#update-the-cli).

`sudo booth repo` refuses on a booth that runs releases: there is no checkout to pull.

## Update the CLI

The CLI ships with each release. Re-run the installer to get the latest one:

```bash
curl -fsSL https://github.com/99Stud/dither_booth/releases/latest/download/install.sh | sudo bash
booth --version
```

`booth update` installs each release's CLI itself. Re-run the installer only on a booth whose CLI predates `booth update`.

## Update the operating system

```bash
sudo apt update && sudo apt full-upgrade -y
sudo rpi-eeprom-update -a
sudo reboot
```

After the reboot, run `booth doctor`. A Chromium update from apt changes the browser the engine renders receipts with; check a test print.

## Roll back

From admin: **System → Software → Roll back**. Over SSH, to go back to the release that ran before the last update:

```bash
sudo booth rollback
```

When the update applied database migrations, the older release can't run on the database as it is, and rollback refuses. It says so and names the backup taken just before the update. Restore it with:

```bash
sudo booth rollback --restore-db
```

Everything the booth recorded after that backup (visits, draws) is lost. Then run `booth doctor`.

<Aside type="danger" title="Migrations don't roll back">
  Migrations are forward-only. `booth update` backs the database up before every
  switch (the last 3 are kept in `/mnt/ssd/dither-booth/backups/`), and only
  that backup takes a booth back across a migration.
</Aside>
